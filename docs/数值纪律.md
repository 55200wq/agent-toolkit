# 数值纪律：有来历，或者明说没有

> 本文件是规则的正文。它跟着工具集走；**skill 里只放指针**，避免两处描述不一致 ✗

## 唯一一条规则

> **你写下的每一个数，要么有实测出处，要么由机制推出，要么当场标明"这是未实测初值"。**
> **不许默默拍一个数，然后拿它当判断依据。**

## 三态（代码里必须命中其一）

```python
STEP_PX = 8.0          # 依据: 机制（由格粒度决定，无需标定）
VAULT_MIN_PX = 0.65    # 依据: 实测（成功翻越 0.55~0.74px，n=3）
STUCK_WINDOW_S = 45    # 依据: 未实测（初值，见 assumptions.json）
STATE_OK = 4           # 依据: 语义（状态码，非可调）
```

| 形态 | 要求 |
|---|---|
| `依据: 实测 …` | 必须能追到项目的实测档案（含 n 与可信度）|
| `依据: 机制 …` | 说明由什么机制决定 |
| `依据: 未实测 …` | 显式承认是拍的 ⇒ 自动进"未实测清单" |
| `依据: 语义 …` | 语义常量（状态码等），非可调 |

**只写"描述"不算依据** ✗（`TIMEOUT = 3.0  # 位移小于此值判为没动` 会被判失败）

## 标注的有效范围（精确规则）

- **同一行**的行尾注释 ✓
- 或**紧邻上方的整行注释块**（中间只能有空行/注释；遇到代码行即停止）✓

⇒ 所以"上面某个常量的行尾标注"不会误罩住下面的常量 ✓（这是自测抓出来的 bug）

## 为什么需要

真实事故（同一会话内连续发生六次）：

| 拍的 | 真相 | 后果 |
|---|---|---|
| 输入延迟 0.5~1.0s | 实测 0.18~0.22s | 按错的前提设计策略 |
| 翻越成功判据 3px | 实测 ≈0.7px | **每次成功翻越都被判失败** ⇒ 永不翻越 |
| "一个身位 ≈6px" | 那是走路位移 | 判据取错 |
| 卡死阈值 0.5px | 被挡时 67~82% 的步 >0.5px | 判据几乎永不触发 |
| 轮询间隔 0.12s | 无任何依据 | 砍掉 3/4 时间分辨率 |

共同点：**写的时候不觉得那是猜** ⇒ 猜测从没进过清单 ⇒ 只能靠人事后抓 ✗

## 做法（四条）

1. 写代码时给每个数值加标签 ✓
2. 写进方案/文档时带上出处 ✓
3. 回复里用到初值要**当场点名** ✓
4. 发现旧代码有没依据的数：**先标注，不要顺手改值** ✗

## 判断标准（自问三句）

1. 这个数错了 2 倍会怎样？（若会"永不触发"或"永远误判"，必须测）
2. 我能说清它怎么来的吗？（说不清 = 拍的）
3. 我把它写进清单、或在回复里点名了吗？

## 边界

- 不要求所有数都测 ✓：策略上限（预算、超时上限）只需标为"策略上限"并说明不影响测量结论
- 不禁止初值 ✓：禁止的是"初值被当成实测依据" ✗
- 机械检查只管**代码里的 4 种写法** ✗：模块级常量 / `self.x = 数字` / 数值表 / `__init__` 签名默认值
- **不查值对错** ✗；**抓不到回复里的错误断言** ✗
