# 脚本小工具：先方案，后实现（plan-first-tooling-zh）

## 唯一一条规则

> **凡是要落成代码的东西，先写方案 → 等评审 → 再实现。**
> 实现出来不符合预期时：**回去改方案，再按新方案改代码。**
> **绝不允许"边写边调"** —— 即靠在真机上反复改参数/试分支来摸出正确行为。

"边写边调"的代价是真实的（本 skill 第 6 节是原始案例）：它把一次性的探索成本
变成"每轮都在真机上跑"的重复成本，产出碎、判断依据散、事后无法复盘。

## 流程（四步，不许跳）

```
① 写方案       落到 docs\方案_<主题>.md（或用户指定位置），内容见 §2 清单
② 等评审       明确问"按这个方案开工吗"；未获同意不动手写实现代码
③ 按方案实现   严格按方案写；方案没写的行为 → 按 scope-drift-guard 处理
④ 不符预期 → 先改方案，再改代码
```

### ③ 实现期的边界

- **方案里写了的**：照做。
- **方案里没写的，但实现时需要**：先停下来问，或按 `scope-drift-guard` 规则处理
  （半自动 → 先问；全自动 → 高亮清单 + 单独文档）。
- **不确定"是不是方案外"**：算方案外，停下来问。

## §2 方案必须回答的清单

一份"详细方案"要让人**只读它就能判断该不该做、做得对不对**。逐条检查：

| # | 必须写清 | 反例（等于没写） |
|---|---|---|
| 1 | **目标与验收**：做完的标志是什么，怎么判断做对了 | "实现一个探测工具" |
| 2 | **明确不做什么**（边界） | 不提边界，最后范围无限膨胀 |
| 3 | **输入/输出契约**：参数、文件格式、stdout/exit code 语义 | "读配置文件"（哪个键？缺了怎么办？） |
| 4 | **数据/时序模型**：时间从哪来、采样率、延迟、单位 | 不写时序，实现时才发现反馈太慢 |
| 5 | **控制流与失败分类**：每类失败怎么判、怎么处置 | 只写"失败就重试"，不分类 → 兜底加重故障 |
| 6 | **关键参数的默认值与依据**：每个可调参数为什么是那个数 | 参数拍脑袋，事后没人知道能不能改 |
| 7 | **验证方式**：怎么证明它对了（离线/单元/真机分段） | "跑一下看看" |
| 8 | **已知局限与不确定项**：哪些没验证、依赖什么前提 | 假装方案完备，坑留给下一个会话 |
| 9 | **实施顺序**：拆成可独立验证的步骤 | 一次写完再调 |

**小工具也别省**：50 行的探测脚本同样要有 §1/§3/§6/§7。可以把方案压进脚本头部
docstring（**先写 docstring 再写代码**），但**不能没有**。

### 方案的"详细"与"啰嗦"之界

详细的判据是：**读完能回答"为什么这样选，不那样选"**。
如果一段话删掉不影响判断，就是啰嗦；如果删掉会让人做出错误实现，就是必要。

## §3 评审怎么问

**半自动化（用户在环内）**：写完后**停下来问**，一次问清最影响方向的少数几个决策
（参考 `grill-me` 的提问方式：给具体选项、推荐项在前），而不是把方案甩过去说"你看看"。

**全自动化（用户不在环内）**：把方案写下来 + **明确列出你替用户做的假设**，
然后继续或停下汇报；不要空转等一个不会有人回答的问题。

## §4 实现不符预期时怎么办 ★本 skill 的重点

这是最容易破功的地方 —— 一看到结果不对，手就自动去改代码了。**必须走这个循环**：

```
1. 停下，先记录"实测现象 + 数据"（日志/截图/数值），不要马上改代码
2. 判断：是"方案错了"还是"实现错了"？
     · 方案错了（假设不成立、时序模型不对、参数依据不成立）→ 改方案
     · 实现错了（漏了方案里写明的分支、抄错参数）→ 直接修，不需改方案
3. 改方案时，把这次的实测证据写进方案的"修订记录"，并**重走评审**
4. 按新方案改代码
```

**判断"方案错了"的典型信号**（任一条成立就去改方案）：

- 实测数据与方案的时序/精度假设矛盾（例：方案假设反馈 200ms，实测 500ms）
- 同一处**改了 2 次以上还没对** —— 说明不是手滑，是模型错了
- 发现方案里某个"依据"其实是猜的
- 需要引入方案里没写的新参数/新分支才能让它工作

**禁止的做法**：

| 禁止 | 为什么 |
|---|---|
| 在真机上连着改参数试（"再试一次 0.3 看看"） | 每轮都是真机成本，且不产生可复用的认知 |
| 边跑边加分支，事后不回头改方案 | 方案与实现脱节，下一个人按方案理解会完全错 |
| 用"兜底"掩盖没搞清的问题 | 兜底会加重故障（本 skill 案例：把"反向移动"当"卡住"去后退脱困） |
| 把不确定的结论写进方案/文档当成结论 | 错误结论比"不知道"更害人 —— 会误导后续实现 |

## §5 与其它 skill 的分工

| skill | 管什么 |
|---|---|
| **本 skill** | **要不要动代码** —— 先方案后实现的门槛 |
| `scope-drift-guard` | **动了以后怎么留痕** —— 方案外变更必须被看见/批准/记录 |
| `grill-me` | **方案怎么问清楚** —— 一次一个问题，把歧义在成本最低时暴露 |
| `handoff-doc-zh` | **怎么交给下一个会话** |

三者串起来是一条链：**先问清（grill-me）→ 写方案评审（本 skill）→ 实现并留痕（scope-drift-guard）**。

## §6 反例（本 skill 的由来）

一次"机器人技巧段执行器"的实现，用户最初的要求只有 5 条。我直接开始写代码，然后：

| 轮次 | 做法 | 结果 |
|---|---|---|
| 1 | 写完就在真机上跑 | 角色**朝反方向冲 41px**（录制只记位置+按键，没记朝向；执行器没管朝向） |
| 2 | 加"朝反方向移动"判据 | 反向被拦住了，但**又暴露过冲 14px**（按时长盲按 + 稀疏位置反馈 → 收不住） |
| 3 | 想调参数收紧 | 用户叫停：**"你先把这个脚本的详细方案写出来，这样乱写太费时间了"** |

事后写方案时才发现，真正该先回答的是三个**时序/模型**问题：

1. 一次"发指令→看到结果"要多久？（实测 130~150ms）
2. 由 1 推出：单次判读的定位误差有多大？（1.8px —— 决定到位阈值不能取 2px）
3. 录制缺了哪一半信息？（**朝向**，得从位置差分推导）

**这三个问题在方案阶段 10 分钟就能想清，而在真机上要靠"冲错 41px + 过冲 14px"两次事故才浮现。**

教训：
- **"先跑跑看"是伪效率**：它把设计问题推迟成调试问题，而调试的每一轮都更贵。
- 用户喊停时说的"乱写"是准确的 —— 不是代码乱，是**没有可对照的规格**，所以每次改动都无法判断对错。
- 正确姿势：**方案里先算出物理下限，再让实现去逼近它**；而不是先实现，再让真机告诉你下限在哪。
