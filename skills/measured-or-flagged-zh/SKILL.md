# 数值：有依据，或者明说没有（measured-or-flagged-zh）

## 唯一一条规则

> **你写下的每一个数，要么有实测出处，要么由机制推出，要么当场标明"这是未实测初值"。**
> **不许默默拍一个数，然后拿它当判断依据。**

## 为什么需要这条

真实事故（同一会话内连续发生）：

| 我拍的 | 真相 | 后果 |
|---|---|---|
| 输入延迟 0.5~1.0s | 实测 0.18~0.22s | 结论错，按错的前提设计策略 |
| 翻越成功判据 3px | 实测成功翻越 ≈0.7px | **每次成功翻越都被判失败**，还写负记录 ⇒ 永不翻越 |
| "一个身位 ≈6px" | 那是走路位移，与翻越无关 | 判据取错 |
| 卡死阈值 0.5px | 被挡时 67~82% 的步 >0.5px | 判据几乎永不触发 |
| 轮询间隔 0.12s | 无任何依据 | 砍掉 3/4 的时间分辨率 |

共同点：**写的时候不觉得那是猜** ⇒ 猜测从没进入任何清单 ⇒ 用户只能一个一个抓 ✗

## 怎么做

### 1. 写代码时：每个数值带「依据」

```python
STEP_PX = 8.0          # 依据: 机制（≈2m 步长，与 CELL 对齐）
VAULT_MIN_PX = 0.65    # 依据: 实测（measured_params.json：成功翻越 0.55~0.74px）
STUCK_WINDOW_S = 45    # 依据: 未实测（初值，见 assumptions.json）
```

- **只写"描述"不算依据**（`# 位移小于此值判为没动` ✗）
- 三态里最优先的是**"由机制决定"**：能选一个不需要标定的值（例如"不额外 sleep，让帧节流定节奏"），
  就不要拍一个数 ✓
- 仓库若有自检（如 `_selftest_provenance.py`），**改完立刻跑** ✓

### 2. 写进方案/文档时：数字后面跟上出处

```
✗ 输入延迟约 0.5~1.0s
✓ 输入延迟 0.18~0.22s（n=14，tools/diag_key_response.py，见 measured_params.json）
✓ 轮询间隔取 0（初值未实测；选择它是因为帧节流已决定节奏，见 assumptions.json）
```

### 3. 回复用户时：把"猜"标出来

- 用了实测值 ⇒ 给出处（文件/工具/n）✓
- 用了初值 ⇒ **当场写"这是初值，尚未实测"** ✓
- 想用但没测过 ⇒ 说"这个数不知道，需要测" ✓，而不是报一个看起来合理的数 ✗

### 4. 反过来：发现旧代码里有没依据的数

不要顺手改值 ✗ —— 先**标注**（标成"未实测"）并加进清单 ✓，再按方案去测 ✓

## 判断标准（自问三句）

1. 这个数如果错了 2 倍，会发生什么？（若会导致"永远不触发"或"永远误判"，就必须测）
2. 我能说清它是怎么来的吗？（说不清 = 拍的）
3. 我有没有把它写进清单、或在回复里点名？（没有 = 还没做完）

## 边界

- **不是要求所有数都测**：策略性上限（迭代预算、超时上限）只需标为"策略上限"并说明它不影响测量结论
- **不是禁止初值**：禁止的是"初值被当成实测依据" ✗
