# 方案外变更守门员（scope-drift-guard）

## 这个 skill 解决什么问题

实施既定方案时，我常会"顺手"加上方案里没写的东西：兜底分支、降级路径、
多一层校验、换个更稳的算法、加个缓存……这些改动**会改变输出行为**，
而用户以为跑的还是原方案。最危险的是**隐式分支**——
用户只有看到反常现象时才知道它的存在。

**本 skill 的唯一目的**：让每一次"超出方案的行为改动"都**被看见**、
**被记录**、且在**半自动化场合被事先批准**。

## 第一步：先判定作业形态

| 形态 | 判据 | 处理方式 |
|---|---|---|
| **半自动化** | 用户在环内：逐步确认、随时插话、每个阶段都会看结果 | **停下来问**，明确同意才做 |
| **全自动化** | 用户不在环内：我按方案连续跑完多步，中途没有逐步批准 | 允许实施，但**必须**完成交付两项（见规则②） |

判定不清时，**按半自动化处理**（更保守的一侧）。

## 规则①：半自动化 → 先问，再做

发现方案外可加/需改的东西时，**不要直接动手**，先说清四件事并征求同意：

1. **是什么**：具体的功能/分支/参数/回退路径
2. **为什么**：不做的后果（会失败？会不稳？只是更好看？）
3. **影响面**：会改哪些文件、哪些数值、哪些控制流；对既有结论是否推翻
4. **回退方式**：怎么撤掉（开关名、还原哪几行、备份在哪）

得到**明确同意**（"加吧""可以""同意"）后才实施。用户沉默/含糊 = 未同意。

## 规则②：全自动化 → 两项强制交付

允许实施，但**缺一不可**：

### 交付 A：最终输出里的高亮清单

在回复中用一个**独立、醒目**的段落（标题含 `⚠️ 方案外变更清单`），逐条列出：

```
⚠️ 方案外变更清单（本次共 N 条）
1. <是什么> ｜ 为什么：<理由> ｜ 影响：<文件/数值/行为> ｜ 回退：<方法>
2. ...
```

**没有方案外变更时也要写**：`⚠️ 方案外变更清单：无（本次严格按方案执行）`。
——这句"无"同样是证据，能防止我事后悄悄补记。

### 交付 B：单独详细文档

写一份独立文档（默认路径 `docs/方案外变更_<YYYYMMDD>_<主题>.md`），内容：

- **原始方案**：方案文档路径 + 相关章节（引用，不复制）
- **实际改动**：逐条列 `文件:行`、改动前后的行为差异（**含数值**）
- **理由与证据**：为什么必须改（实测数据、报错、失败复现）
- **验证方法**：怎么确认改动生效且没引入回归（**可复现的命令**）
- **回退步骤**：逐条可执行（还原哪个文件/改哪个参数/备份路径）
- **未验证/已知风险**：诚实列出没测到的部分

最终输出中给出该文档的**路径链接**，不能只说"我写了文档"。

## 规则③（通用）：方案文档必须同步更新

方案一旦被改动（含方案外新增、删除、回退分支、参数变更），**必须同步更新方案文档本身**：

1. 在方案文档中加**「修订记录」**段（保留原方案正文，不抹掉、不静默覆盖）：
   `YYYY-MM-DD ｜ 改了什么(章节/条目) ｜ 为什么 ｜ 生效范围 ｜ 关联变更文档路径`
2. **两份文档互相链接**：方案文档 ↔ 方案外变更详细文档
3. 找不到方案文档时：**先问"方案文档在哪"**，不允许默认跳过同步

## 什么算"方案外变更"（判定标准）

**算**（必须声明）：
- 任何**影响输出数值**的分支、常量、阈值、默认参数
- 任何**影响控制流**的：回退路径、降级模式、重试、跳过条件、提前返回 None
- **隐式行为**：方案没写、但代码里存在的"失败就改用另一条路"——**一律算**，
  这正是最容易伤人的一类（例：拟合失败就悄悄改用另一种算角度的方法）
- 新增依赖、新增文件、改变接口签名或返回值语义

**不算**（不必单列，但可在交付里一句话带过）：
- 纯注释、日志文案、变量/函数重命名（不改行为）
- 格式、缩进、import 顺序
- 用户当场要求的东西

**边界不明时 → 算**。

## 交付前自查清单（逐条过）

- [ ] diff 里有没有方案没提过的新分支、新常量、新参数、新的失败处理？
- [ ] 有没有"失败就回退到备用算法/最远点/上一帧"这类**隐式兜底**？
- [ ] 有没有为了提高成功率而**放宽/收紧**某个阈值？
- [ ] 返回值/异常语义变了吗（原来可能抛、现在返回 None）？
- [ ] 方案文档更新了吗？两份文档互相链接了吗？
- [ ] 全自动化场合：高亮清单与详细文档都产出了吗？路径给了吗？

## 反例（这条 skill 的由来）

某次全自动化作业中，我在补丁里给"两条边线求交点"加了一个**未声明的回退**：
交点不满足质量门时，改用"轮廓最远点"当尖端。方案里没有这条分支，
日志里也没标。后果：用户看到"方向线不穿过交点"的反常现象，
排查了半天才发现存在一条他从不知道的降级路径。

**正确做法**：实施前问（半自动化），或实施后高亮 + 单独文档 + 方案文档修订记录（全自动化）。
