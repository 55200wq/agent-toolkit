# 沙箱设备访问诊断（sandbox-device-access-zh）

## 唯一一条规则

> **设备打不开时，第一个怀疑对象是沙箱/权限，不是设备、不是后端、不是格式。**

**判据（最强信号）**：

> **同一份代码 + 同一台机器 + 用户能跑通 + 我跑不通 ⇒ 是权限/沙箱。**

满足这条时，**不要**再去试格式、索引、分辨率、后端、驱动——那些不可能解释"用户跑得通"。
`激活 Media Source 失败`、`拒绝访问`、`PermissionError`、`EACCES/EPERM`、`device busy`
这类**权限味道的报错**，一律先当成权限问题处理。

## 第一步：按这个顺序查（不要跳步）

```
① 权限/沙箱层   ← 先查这里！（本 skill 的全部重点）
   · 当前文件策略 / 沙箱模式是什么？
   · 这个设备在当前沙箱模式下是否在允许清单里？（采集类设备常被默认排除）
   · 同一命令放到"未受限"的执行路径下是否立刻成功？
② 基线程序
   · 宿主自带程序能否打开同一设备？（Windows 相机 App / macOS Photo Booth / Linux cheese）
   · 能 → 设备与驱动正常，回到 ①
   · 不能 → 才轮到"设备真被占用 / 驱动异常 / 没信号"
③ 占用与信号
   · 有没有别的进程握着设备？（占用类错误才需要走到这）
   · 设备有信号/上电吗？（采集卡无 HDMI 信号时可能根本不注册为可用源）
④ 调用参数
   · 格式 / 索引 / 分辨率 / 后端 —— 只有 ①②③ 全部排除后才查这里
```

**为什么把 ④ 放最后**：格式和后端有几十种组合，试起来极快、看起来"很努力"，
但**解释不了"用户能跑通"**。先试 ④ 只会把时间烧光（见下方反例）。

## ② 的做法：用"最小可复现 + 基线对照"

写一个**十行以内**的探针，只做两件事：打印当前沙箱状态 + 尝试打开设备。

```python
import os, sys, cv2
print("DSH_* 环境变量:", {k: v for k, v in os.environ.items() if k.startswith("DSH_")})
cap = cv2.VideoCapture(0)            # 摄像头/采集卡；串口换成 pyserial 的 Serial(...).open()
print("open =", cap.isOpened())
ok = False
if cap.isOpened():
    for _ in range(50):
        r, f = cap.read()
        if r and f is not None and getattr(f, "size", 0):
            print("frame =", f.shape); ok = True; break
print("结论:", "能打开 ✓" if ok else "打不开 ✗")
```

**探针必须同时能在"用户自己的终端"里跑**——两边的输出一比，答案立刻出来：

| 我的沙箱 | 用户终端 | 结论 |
|---|---|---|
| ✗ | ✓ | **权限/沙箱**（本 skill 的主场景）→ 去 ① |
| ✗ | ✗ | 设备真的不可用 → 去 ③ |
| ✓ | ✓ | 设备没问题，回去看业务逻辑（此时才轮到 ④ 和业务代码） |

## ① 的做法：怎么确认/解决权限

1. **读环境自报**：优先看宿主注入的沙箱/策略变量（如 `DSH_*`）、以及宿主在
   每轮对话开始时给出的策略声明（文件策略、审批策略）。
2. **确认差异**：把同一命令放到未受限的执行路径下跑一次。**这是判定性实验**，
   成功即结案，不要再去调参数。
3. **提权重试要"窄"**：只对**那一条**失败的命令申请更宽的权限，并说明为什么必须更宽；
   不要为了省事把整轮都放宽。
4. **改不动就换分工**：若沙箱策略不允许放宽，让用户在他的终端里跑（日志落盘到工作区，
   我读文件分析）。这个分工是**可接受的正解**，不是失败。

### 跨平台要点

| 平台 | 设备访问的权限关口 |
|---|---|
| Windows | 沙箱策略（DSH 文件策略会影响设备访问）；系统相机隐私开关；`ERROR_ACCESS_DENIED`/`0x80070005`；Media Foundation 对无信号设备可能激活失败 |
| Linux | 设备节点权限与组（`/dev/video*`、`/dev/ttyUSB*` → `video`/`dialout` 组）；容器需 `--device`；SELinux/AppArmor |
| macOS | TCC 隐私授权（摄像头/麦克风），终端或宿主 App 必须被授权 |

## 分清两类"打不开"

| 类型 | 典型报错 | 处置 |
|---|---|---|
| **权限/沙箱** | 拒绝访问、`EACCES`/`EPERM`、`0x80070005`、`激活 Media Source 失败` | 查 ①，**不要**碰格式/后端 |
| **真占用/真无信号** | `device or resource busy`、`EBUSY`、`已被占用`、打开成功但读不到帧 | 才去 ③：找占用进程 / 查信号与供电 |

注意：**厂商/自研模块常把两者混成一句话**——例如 `打开失败（可能仍被占用）` 里
"被占用"是作者猜的，实际原因可能是权限。**不要相信括号里的归因**，自己验。

## 移交前必做：把结论写进产物

诊断一旦定位到权限/沙箱，**当场记录**（否则下一个人重走一遍）：

- 报错原文 + 判定性实验（做了哪个改动后立刻成功）
- **明确写下"我一度误判成 X，实际是 Y"**——错误结论比没有结论更害人
- 把"先查权限"这条顺序写进项目的踩坑记录

## 反例（本 skill 的由来）

一次实机任务里，采集卡打不开，报 `激活 Media Source 失败`。我按下面的顺序烧掉了大量时间：

1. 试了三种格式（YUY2 / XRGB / NV12）× 两个设备索引 × 三个后端（自研模块 / DSHOW / MSMF）→ 全失败
2. 杀掉两批"疑似占用"的进程 → 无效
3. 查环境变量、改调用顺序、验证设备枚举 → 无效
4. 发现自己在 Windows **会话 2**、交互桌面在**会话 1**，**误判为"跨会话设备隔离"**并写进了方案文档
5. 还推断过一次"ROI 特征集为空导致死锁"——同样错了

真实原因：**沙箱策略没有给设备访问权限**。用户把文件策略放开后，**同一会话立刻成功**，
一行代码都没改。

教训：
- 第 1 步就错了——**用户说"我能打开"时，答案已经写在墙上了：那是权限**。
- 中间的"会话隔离""空特征集"都是**看起来深刻的错误结论**，比"我不知道"更危险，
  因为它们会被写进文档误导后人。
- 顺序应该是：**先问"我是不是被限制了"，再问"设备怎么了"，最后才问"参数对不对"。**
